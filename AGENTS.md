# AGENTS.md

## Проект и карта репозитория

MoloTalk — веб-мессенджер для личной и групповой переписки. Сервисы на Go, клиент на React и TypeScript. PostgreSQL хранит данные, Redis — присутствие, NATS Core доставляет события, MinIO хранит файлы. Caddy принимает трафик, Docker Compose поднимает окружение. ConnectRPC использует protobuf-контракты из `api/`.

| Путь | Назначение |
| --- | --- |
| `backend/` | Go-сервисы, платформенные компоненты и миграции. |
| `api/` | Proto, конфигурация генерации и контракты OpenAPI. |
| `web/` | Веб-клиент и его тесты. |
| `deploy/` | Compose, Caddy и проверки окружения. |
| [`docs/`](docs/README.md) | Индекс FS, HLD и исходников диаграмм. |
| `openspec/` | Действующие спецификации в `specs/`, изменения в `changes/`. |
| `.github/` | Шаблоны issue и PR. |

Общий процесс участия и Definition of Done описаны в [CONTRIBUTING.md](CONTRIBUTING.md). Следуй [порядку источников](docs/README.md#порядок-источников). Требования бери из FS, архитектурные решения — из HLD, уточнения — из действующих спецификаций OpenSpec.

## Сборка, проверки и запуск

| Каталог запуска | Команда | Назначение |
| --- | --- | --- |
| Корень | `docker compose --project-directory . --env-file .env.example -f deploy/docker-compose.yml up --build --wait --wait-timeout 180` | Запуск окружения по [README](README.md#запуск-окружения). |
| `backend/` | `go build ./...`, `go vet ./...`, `go test -count=1 ./...` | Сборка и обычные проверки Go. Версия Go указана в `go.mod`. |
| `backend/` | `go test -tags=integration -count=1 ./...` | Интеграционные тесты с Docker. |
| Корень | `npm ci` | Установка зависимостей api и web из общего `package-lock.json` (workspaces). |
| `api/` | `buf generate --template buf.gen.go.yaml`, `buf.gen.ts.yaml`, `buf.gen.openapi.*.yaml` | Генерация контрактов по [api/README.md](api/README.md#команды). |

## Рабочий цикл карточки

Один issue = одна ветка = одно изменение OpenSpec = один PR.

1. Прочитай issue, связанные требования FS по ID, разделы HLD и релевантные спецификации в `openspec/specs/`.
2. Работай в ветке этой карточки от `main`. Создай изменение OpenSpec с `proposal.md`, `design.md`, дельтами в `specs/` и `tasks.md`.
3. Запусти `openspec validate <change-id> --strict`. Покажи предложение и результат проверки. **Остановись и дождись явного одобрения человека перед реализацией.**
4. После одобрения реализуй изменение по `tasks.md`. Отмечай выполненные задачи после соответствующих проверок.
5. Запусти целевые тесты и проверки затронутых компонентов. Подготовь один PR по [шаблону](.github/PULL_REQUEST_TEMPLATE.md) и итоговый отчёт.

Веди каждую карточку отдельно. Для чужих дефектов заводи отдельный issue вместо попутных правок. После реализации попроси человека архивировать изменение OpenSpec, желательно в рамках того же PR. Архивацию выполняет человек.

## Принципы реализации

- Сначала используй стандартную библиотеку, затем проверенную стороннюю. Самописную инфраструктуру обосновывай в `design.md`.
- Для каждой новой зависимости укажи причину выбора и лицензию в `Decisions` файла `design.md`.

## Архитектура и контракты

Смотри [HLD §2](docs/hld/02-architecture.md) и [§5.1–5.3](docs/hld/05-testability.md#section-5-1).

- Бизнес-логика находится в прикладном или доменном слое. Обработчики и контроллеры занимаются транспортом и передачей управления.
- Порты объявляет потребитель. Подключай реализации в точках сборки. Доступ к БД, брокеру, файловому хранилищу, времени, ID и случайности идёт через порты, например `Clock`, `IDGenerator`, `MemberChooser`.
- Прямые импорты между прикладными модулями запрещены.
- Общие пределы, например 4096 символов и 5 вложений, закреплены в proto и миграциях. При изменении предела согласованно обновляй proto, схему через миграцию и тесты.
- Proto — единственный источник типов, сервисов и правил валидации API. Артефакты в `backend/gen/`, `api/src/gen/` и `api/gen/` обновляй генерацией. После изменения proto запускай проверку генерации.

## Тесты

- В каждом тесте явно проверяй ожидаемый результат или состояние.
- Для детерминированных тестов подставляй время, ID и случайность через порты.
- Для затронутых правил применяй классы эквивалентности, граничные значения и таблицы решений по ситуации.
- Интеграционные Go-тесты помечай `//go:build integration`.

## Безопасность и журналирование

- Секреты, пароли и токены запрещено хранить в коде и выводить в ошибки или журналы.
- Наружу отдавай безопасную ошибку. Причину записывай в журнал в безопасной форме с `request_id`.

## Git

- Прямые коммиты в `main` запрещены.
- Коммиты оформляй по Conventional Commits с областью `auth`, `chat`, `media`, `presence`, `gateway`, `web`, `api`, `db`, `infra` или `docs`. Например, `feat(chat): add message pagination`.

## Итоговый отчёт

1. Что изменено.
2. Как проверено — команды и фактический результат.
3. Что не проверено и почему.
4. Отклонения и открытые вопросы.
