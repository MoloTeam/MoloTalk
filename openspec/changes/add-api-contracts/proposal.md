# Proposal

## Why

Issue [#6](https://github.com/MoloTeam/MoloTalk/issues/6) закрепляет общий контракт для параллельной разработки сервисов и клиента. Единственный источник типов и ограничений — proto, производные Go, TypeScript и OpenAPI воспроизводятся готовыми инструментами.

## What Changes

- Описать 29 внешних RPC в `molotalk.v1` и 5 внутренних в `molotalk.internal.v1`. TypeScript-клиент генерировать только для публичного пакета. Пути внешних RPC сохранить.
- **BREAKING относительно материалов HLD:** заменить строковые доменные значения настоящими proto-enum со стандартными именами Buf, Timestamp — `google.protobuf.Timestamp`, пустые сообщения — `google.protobuf.Empty`. Использовать `int32` для ограниченных чисел, включая sizeBytes, вместо его прежней JSON-строки.
- Задать ограничения через protovalidate. OpenAPI 3.1 получать `protoc-gen-connect-openapi`. Security задавать штатным base-файлом, обязательность допускающих пустое значение массивов описать стандартной аннотацией. Ограничения генератора и причины исключений перечислены в design.
- Выполнить одноразовую содержательную сверку с `openapi.json` HLD с учётом утверждённых отклонений. Затем использовать golden-файл, обычный diff и `buf breaking`, без собственного компаратора схем.
- Закрепить инструменты через `tool` в Go-модуле и `package-lock.json`. Команды generate/check не требуют Docker.
- Зафиксировать ReceiptUpdated с chatId, messageId и ровно одним из receiptSummary/receipt. Автор получает сводку, сеансы читателя — только собственное подтверждение.
- **BREAKING относительно материалов HLD:** в срезе C использовать утверждённый владельцем вариант B — типизированные GatewayEnvelope и ServerEvent с обязательными oneof. JSON внутри payload, data_json, opcode, sequence и прежние резервные значения исключаются.

## Capabilities

### New Capabilities

- `rpc-contracts` — состав RPC, типы, декларативная валидация и единый формат ошибок.
- `contract-generation` — генерация из proto, стандартные проверки и воспроизводимость производных файлов.
- `gateway-contracts` — типизированные protobuf-кадры и события WebSocket по утверждённому варианту B.

### Modified Capabilities

Нет. Внешние маршруты `ingress-routing` и поведение `observability` сохраняются. Изменение имён внутренних RPC не меняет существующий запрет их внешнего доступа.

## Impact

Реализация планируется в этой же ветке `feat/6-api-contracts`. Области — `api/`, `backend/gen/`, зависимости генерации и минимальные общие транспортные адаптеры. Прикладные модули не должны зависеть от транспортных типов внутри доменной логики.

Основой служат актуальные HLD §5.1–5.8, материалы контрактов и форматные ограничения схемы #5. Таблица «Отклонения от HLD» в design предназначена для журнала изменений владельца. Снимки источников и фактические результаты исследования инструментов также зафиксированы там.

В issue #6 не входят бизнес-обработчики, подключение RPC к main, сетевой Gateway, управление сеансами, миграции/fixtures, изменение HLD, Caddy, Compose приложения и CI. Потребителям внутренних RPC позднее потребуется использовать новые сгенерированные сервисы. Outbox, проксирование файлов и replay не добавляются.

## Закрытые вопросы

- **Q1:** proto — единственный источник типов и правил protovalidate. OpenAPI генерируется; base-файл содержит только недостающую HTTP-метаинформацию. Содержательная сверка с HLD выполняется один раз, затем применяется golden.
- **Q2:** enum, WKT, optional, int32 и явная выдача false/0/[] заданы владельцем. Произвольных int64 в прикладных DTO после аудита не остаётся.
- **Q3:** поля и аудитории ReceiptUpdated определены владельцем. Правило ровно одного содержательного поля выражается `(buf.validate.message).oneof` с `required: true`.
- **Q4:** инструменты закрепляются без контейнера, Go-инструменты через `tool`, JS через lock-файл. Совместимость проверяет `buf breaking`.
- **Gateway, срез C:** владелец утвердил вариант B. Оболочка содержит oneof Identify/Ready/Heartbeat/HeartbeatAck/ServerEvent; ServerEvent — oneof восьми событий. Решение заменяет смешанный protobuf/JSON из HLD §5.8 и требует последующего обновления этого раздела отчёта.

## Открытые вопросы

Открытых вопросов нет. Формат Gateway согласован; срезы A, B и C входят в план реализации без дополнительного согласования выбора протокола. Утверждение решения не означает выполнения задач реализации.
