# Design

## Context

Мотивация и границы приведены в [proposal.md](proposal.md). В репозитории есть Go-модуль `backend/`, пять команд `cmd/`, корневой `.env.example` и HTTP-каркас с `/healthz` и `/readyz`. При пустом наборе проверок `/readyz` возвращает `503`. На момент исследования Compose, Dockerfile и веб-клиент отсутствуют. В слитой реализации зависимости хранения ещё не подключены.

Основной контракт окружения опирается на HLD §3.1, §3.3 и §6.4. Предыдущий change `add-backend-skeleton` хранит поведение backend-health и HTTP-корреляции. Новые дельты описывают только контейнерное окружение и прокси.

## Goals / Non-Goals

**Goals**

- Обеспечить одинаковую последовательность запуска и проверяемое поведение при ошибках подготовки.
- Развести адреса внутри контейнерной сети и адреса, доступные с хоста.
- Сделать проверку маршрутизации независимой от появления бизнес-обработчиков.

**Non-Goals**

- Миграции и fixture реализуются в #5, клиент — в #7, рабочий WebSocket — в Gateway, реальные backend-readiness — в T-32.
- Прикладные адаптеры и их TTL подключаются в соответствующих карточках.

## Decisions

### Размещение и запуск

Основной файл — `deploy/docker-compose.yml`, прокси — `deploy/Caddyfile`, сборка backend — `backend/Dockerfile`. Корневой `.dockerignore` ограничивает контекст сборки исходниками и материалами, нужными Dockerfile.

Каноническая команда выполняется из корня репозитория.

```text
docker compose --project-directory . --env-file .env.example -f deploy/docker-compose.yml up --build --wait --wait-timeout 180
```

Для личных значений разработчик передаёт `--env-file .env`. Явные пути исключают зависимость от поиска `.env` рядом с Compose в `deploy/`. README предупреждает о приоритете переменных shell. Образы фиксируются доступными тегами и digest при реализации. Версия Go в builder должна удовлетворять существующему `backend/go.mod`.

### Сборка пяти процессов

Один многостадийный Dockerfile использует отдельные целевые стадии для пяти бинарников. Builder получает `go.mod` и `go.sum` до исходников для кеширования зависимостей. Итоговые образы содержат бинарник и инструмент HTTP-проверки, проверенный при сборке. Это позволяет Compose выполнять healthcheck внутри контейнера. Сборка каждого образа из одного builder сохраняет единую версию Go.

Compose явно передаёт `HTTP_HOST=0.0.0.0`. Имена процессов и переменные портов сохраняют контракт каркаса. Внутренние клиенты используют DNS-имена служб Compose. По умолчанию backend, PostgreSQL, Redis и NATS доступны внутри сети. Публикация Caddy и прямого S3-порта привязана к loopback хоста.

### Конфигурация и данные

В `.env.example` добавляются используемые Compose значения PostgreSQL, MinIO, имя bucket и внешний HTTPS-порт. Для Caddy внешний порт по умолчанию — `443`, для прямого локального S3-доступа — `9000`. Все credentials примера помечаются тестовыми. Обязательные непустые значения проверяются до инициализации. Настройки инфраструктуры передаются её контейнерам; backend получает только используемые им настройки.

Имена volumes принадлежат Compose-проекту. Сохраняются данные PostgreSQL, MinIO и каталог данных Caddy с CA. Остановка через `down` сохраняет их; `down -v` документируется отдельно с указанием удаления данных выбранного окружения. NATS работает в Core-режиме.

Внутренний адрес MinIO служит подготовке bucket. Опубликованный S3 endpoint предназначен для прямого доступа с хоста. Параметр внешнего endpoint для подписывания URL подключит Media при реализации выдачи ссылок. Рабочая цепочка браузер → S3, включая HTTPS и CORS, проверяется в карточке Media.

### Порядок запуска

PostgreSQL, Redis, NATS и MinIO стартуют с собственными healthcheck. Для PostgreSQL используется проверка готовности подключений, для Redis — PING, для NATS — HTTP health endpoint внутреннего monitoring-порта, для MinIO — штатный endpoint готовности. Для каждого выбранного образа проверяется наличие исполняемого средства проверки. Интервал, стартовый период и число попыток дают достаточный бюджет холодного запуска и ограничивают ожидание ошибки.

Одноразовая служба `minio-init` ждёт `service_healthy` MinIO. Она создаёт bucket через клиент MinIO и устанавливает закрытую анонимную политику. Существующий bucket допускается, прочие ошибки сохраняют ненулевой код. Проверка credentials предшествует попытке создания. Нельзя подавлять все ошибки создания bucket как признак его существования.

Пять процессов ожидают успешных инфраструктурных проверок и `service_completed_successfully` для `minio-init`. Их healthcheck обращается к `/healthz`; затем запускается Caddy. Для Caddy отдельная служебная проверка подтверждает работу прокси и не зависит от пока отсутствующего веб-клиента.

Эта цепочка обеспечивает подготовку окружения #4. В #5 добавятся задачи миграций и fixture с проверкой успешного завершения перед запуском backend. Пустые задания, маскирующие выполненную подготовку БД, не создаются. Повторная оценка обязательных зависимостей при работающем backend относится к T-32.

### HTTPS и правила Caddy

Caddy обслуживает `localhost` с `tls internal` и сохраняет CA в volume. README описывает получение публичного сертификата CA и доверие на Windows и других поддерживаемых ОС. Закрытый ключ остаётся в volume. Проверочные команды передают публичный CA явно. Настройка доверия браузера выполняется разработчиком один раз для данного CA.

Маршруты задаются точными путями из [ingress-routing](specs/ingress-routing/spec.md). Сначала проверяются RPC и `/ws`, затем корневой маршрут и ответ `404` для остальных запросов. Для RPC разрешён метод POST. Caddy сохраняет путь и тело запроса; допустимый `X-Request-Id` проходит до backend и обратно. Широкое совпадение по имени сервиса открыло бы внутренние методы, поэтому используется список разрешённых путей.

Маршрут `/ws` использует штатное проксирование Upgrade. В текущем каркасе обработчик Gateway ещё отсутствует. Корень возвращает `503` до #7. Эти состояния описываются в README, чтобы успешный запуск Compose не воспринимался как готовность пользовательского сценария.

### Проверки окружения

Материалы проверки располагаются в `deploy/tests/`. Изолированный Compose-проект получает собственные volumes и порты. Для маршрутизации конфигурация теста заменяет upstream контейнерами, которые фиксируют запросы и отвечают контрольными данными; тестовый Gateway поддерживает Upgrade и контрольный обмен кадрами. Тестовые реализации остаются в проверочном контуре.

Проверяются все разрешённые RPC, пять внутренних методов, неизвестные пути, соседние пути и HTTP-корреляция. Проверка TLS доверяет полученному CA. Подготовка bucket проверяется первым и повторным запуском, существующим объектом, открытой исходной политикой и неверными credentials. Проверка перезапуска создаёт служебную контрольную таблицу через SQL-клиент в отдельном окружении. Она не вводит прикладную схему или fixture.

## Risks / Trade-offs

- Изменение образа нарушает healthcheck → фиксировать версию образа, проверять средство проверки в итоговом контейнере.
- Стартовый healthcheck принимают за полную готовность приложения → README и сценарии явно фиксируют текущее `/readyz → 503` и границу T-32.
- Первый запуск без сети не может загрузить образы и Go-зависимости → указать сетевые предпосылки; повторные сборки используют локальный кеш.
- Браузер не доверяет локальному CA → описать установку доверия и проверку сертификата; сохранить CA между перезапусками.
- Сбой подготовки скрыт повторным запуском → сохранить код завершения init-контейнера и диагностировать его через Compose logs.
- Позднее подключение миграций меняет цепочку запуска → #5 добавляет собственные задания и проверяет новую последовательность до backend.

## Migration Plan

Прикладные данные этим change не мигрируют. После слияния первый запуск создаёт volumes и bucket. При изменении конфигурации контейнеры пересоздаются документированной командой; существующие данные сохраняются. Откат конфигурации выполняется на предыдущую совместимую версию с сохранением volumes. Возврат к чистому тестовому состоянию требует отдельной явной очистки.
