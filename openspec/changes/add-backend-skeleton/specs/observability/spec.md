# Observability

## Purpose

Позволяет связать HTTP-запросы, ответы и записи серверного журнала. Основание — HLD §5.1 для передачи `X-Request-Id` и §6.5 для состава журнала и исключения секретов.

## ADDED Requirements

### Requirement: Выбор идентификатора HTTP-запроса

После разбора HTTP сервис SHALL сохранять ровно одно значение `X-Request-Id`, соответствующее `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Если заголовок отсутствует, пуст, повторяется или нарушает этот формат, сервис SHALL назначить новый ULID и продолжить обработку запроса.

#### Scenario: Допустимая длина включает обе границы

- **GIVEN** отдельные запросы к `/healthz` содержат по одному допустимому `X-Request-Id` длиной 1 и 64 ASCII-символа
- **WHEN** сервис отвечает на запросы
- **THEN** в каждом ответе `X-Request-Id` совпадает с переданным значением

#### Scenario: Отсутствующий идентификатор формируется для каждого запроса

- **GIVEN** два независимых запроса к `/healthz` без `X-Request-Id`
- **WHEN** сервис отвечает на оба запроса
- **THEN** ответы содержат два разных допустимых ULID в `X-Request-Id`

#### Scenario: Недопустимое или неоднозначное значение заменяется

- **GIVEN** в отдельных запросах к `/healthz` заголовок пуст, содержит 65 символов, начинается с точки, содержит запятую или передан дважды
- **WHEN** HTTP-запросы разобраны и сервис обрабатывает их
- **THEN** каждый запрос получает `200 OK` и новый допустимый ULID в `X-Request-Id`, который используется в журнале вместо входного значения

### Requirement: Передача идентификатора по HTTP

Сервис SHALL использовать итоговый идентификатор в контексте операции, передавать его в `X-Request-Id` внутренних HTTP-вызовов, возвращать в заголовке ответа и записывать в `request_id` журнала. Правило SHALL применяться к успешным ответам и ошибкам.

#### Scenario: Внутренний вызов получает идентификатор исходной операции

- **GIVEN** входящая HTTP-операция с допустимым `X-Request-Id` вызывает внутренний HTTP-адаптер
- **WHEN** адаптер отправляет запрос и сервис возвращает результат операции
- **THEN** исходное значение присутствует в заголовках внутреннего запроса и внешнего ответа, а также в поле `request_id` записи операции

#### Scenario: Ответ об отказе коррелирует с журналом

- **GIVEN** запрос к `/readyz` содержит допустимый `X-Request-Id`, а подставленная проверка готовности возвращает ошибку
- **WHEN** сервис возвращает `503 Service Unavailable`
- **THEN** заголовок ответа и `request_id` записи об отказе совпадают с входным идентификатором

### Requirement: Структурированная запись результата

Запись результата операции SHALL содержать `request_id`, сервис, имя операции, результат и длительность. Идентификаторы пользователя, чата и сообщения SHALL добавляться при наличии в проверенном контексте операции.

#### Scenario: Журнал различает готовность и отказ

- **GIVEN** подстановка `ReadinessCheck` при первом вызове `/readyz` возвращает успех, а при втором — ошибку
- **WHEN** сервис отвечает на оба запроса
- **THEN** записи содержат обязательные поля и различимые результаты готовности и отказа

### Requirement: Исключение секретов из журнала

Сервис SHALL исключать из записей и сообщений об ошибках пароли, токены, значение заголовка `Authorization`, секреты конфигурации и содержимое файлов.

#### Scenario: Ошибка зависимости содержит контрольный секрет

- **GIVEN** подстановка `ReadinessCheck` возвращает ошибку с контрольным секретом конфигурации, а запрос к `/readyz` содержит тестовый токен в `Authorization`
- **WHEN** сервис отвечает `503 Service Unavailable` и записывает результат
- **THEN** запись содержит обязательные поля, значение секретной настройки и токен отсутствуют в журнале
