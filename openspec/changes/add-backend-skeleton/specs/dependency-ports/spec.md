# Dependency Ports

## Purpose

Определяет серверные интерфейсы подмены инфраструктуры и источников недетерминированности. Основание — HLD §6.1 для границ модулей, §6.2 и таблица 11 для портов, §6.3 для времени, идентификаторов и выбора кандидата.

## ADDED Requirements

### Requirement: Порты аккаунтов и сеансов

Backend SHALL предоставлять следующие порты из таблицы 11 HLD.

- `AccountRepository` — `FindByIdentifier`, `Create`, `Update`.
- `SessionRepository` — `ConsumeRefresh`, `Revoke`.
- `PasswordHasher` — `Hash`, `Verify`.
- `TokenCodec` — `Issue`, `Validate`.

#### Scenario: Auth получает операции через порты

- **GIVEN** тестовые реализации всех четырёх интерфейсов аккаунтов и сеансов
- **WHEN** компиляционная проверка обращается к перечисленным методам через эти интерфейсы
- **THEN** контракт доступен потребителю без импорта реализаций хранения, хеширования или токенов

### Requirement: Порты состава чата, сообщений и транзакций

Backend SHALL предоставлять следующие порты из таблицы 11 HLD.

- `ChatRepository` — `GetMembers`, `LockGroup`, `AddMember`, `ChangeOwner`.
- `MessageRepository` — `CreateOrGet`, `UpdateVersion`, `SoftDelete`, `ListRange`.
- `ReceiptRepository` — `UpsertMonotonic`, `GetSummary`, `GetReadStates`.
- `GroupUnitOfWork` — `WithinTransaction`.

#### Scenario: Chat получает состав и транзакцию через разные порты

- **GIVEN** тестовые реализации `ChatRepository` и `GroupUnitOfWork`
- **WHEN** тестовый потребитель обращается к методам состава и вызывает `WithinTransaction` через интерфейсы
- **THEN** код компилируется с обоими портами без подключения к PostgreSQL

#### Scenario: Сообщения и подтверждения доступны модулю Chat

- **GIVEN** тестовые реализации `MessageRepository` и `ReceiptRepository`
- **WHEN** тестовый потребитель вызывает `SoftDelete` и `GetSummary` через интерфейсы
- **THEN** код компилируется без подключения к PostgreSQL, а модуль Media этих портов не требует

### Requirement: Порты вложений

Backend SHALL предоставлять следующие порты из таблицы 11 HLD.

- `AttachmentRepository` — `Get`, `MarkReady`, `Link`, `CheckReferences`.

#### Scenario: Ошибка привязки воспроизводится в изоляции

- **GIVEN** подстановка `AttachmentRepository` возвращает заданную ошибку из `Link`
- **WHEN** тест обращается к `Link` через порт
- **THEN** тест получает ожидаемую ошибку без обращения к БД или файловому хранилищу

### Requirement: Порты объектов и обмена событиями

Backend SHALL предоставлять следующие порты из таблицы 11 HLD.

- `ObjectStorage` — `PresignPut`, `PresignGet`, `Open`, `Finalize`, `Head`, `Delete`.
- `EventPublisher` — `Publish`.
- `EventSubscriber` — `Subscribe`.

#### Scenario: Отказ объекта и публикации воспроизводится через порты

- **GIVEN** подстановки `ObjectStorage` и `EventPublisher` настроены на заданные ошибки, S3 и NATS недоступны
- **WHEN** тест вызывает `Head` и `Publish` через соответствующие интерфейсы с контекстом операции
- **THEN** каждый вызов возвращает ожидаемую по своему контракту ошибку без подключения к S3 или NATS

### Requirement: Межсервисные порты и состояние присутствия

Backend SHALL предоставлять следующие порты из таблицы 11 HLD.

- `AuthClient` — `CheckSession`.
- `ChatAccessClient` — `CheckAccess`, `GetAudience`.
- `PresenceStateStore` — `Renew`, `Remove`, `ListLive`. TTL ведётся для каждого подключения: `Presence` содержит `ConnectionID`, а `Remove` закрывает конкретное подключение, а не все подключения пользователя.

#### Scenario: Контракты доступны без межсервисной сети

- **GIVEN** тестовые реализации `AuthClient`, `ChatAccessClient` и `PresenceStateStore`
- **WHEN** компиляционная проверка обращается к перечисленным методам через соответствующие интерфейсы
- **THEN** код проверки компилируется без реализации HTTP-клиентов или Redis

#### Scenario: Закрытие одного подключения не затрагивает другое

- **GIVEN** у пользователя два активных подключения в одном чате
- **WHEN** закрывают первое подключение через `Remove` с его `ConnectionID`
- **THEN** `ListLive` возвращает второе подключение без изменений

### Requirement: Сборка модулей в точке входа

По HLD §6.1–6.2 модули SHALL получать порты через конструкторы. Точка входа `main` SHALL связывать их с реализациями. Прикладной и доменный код SHALL обращаться к БД, брокеру и файловой системе через порты. Операции ввода-вывода SHALL принимать контекст операции, а отказы SHALL быть различимы по контракту порта.

#### Scenario: Модуль можно собрать в изоляции

- **GIVEN** для модуля доступны тестовые реализации всех его портов, а сеть и локальное хранилище недоступны
- **WHEN** модуль создают через конструктор с этими реализациями
- **THEN** модуль создаётся без сетевых подключений и доступа к локальному хранилищу

#### Scenario: Архитектурные границы проверяются в исходниках

- **GIVEN** точки входа пяти сервисов и исходники их прикладных и доменных модулей
- **WHEN** проверяют, где создаются инфраструктурные зависимости и откуда они вызываются
- **THEN** реализации связываются с модулями в точках входа, а в прикладном и доменном коде отсутствуют прямые обращения к глобальному пулу БД, брокеру и файловой системе

### Requirement: Управляемое время

По HLD §6.3 интерфейс `Clock.Now` SHALL предоставлять текущее время. Боевая реализация SHALL читать системные часы, тестовая — управляемую шкалу времени.

#### Scenario: Тестовое время изменяется только по явной команде

- **GIVEN** тестовые часы установлены на `2026-10-19T09:00:00Z`
- **WHEN** время читают дважды, продвигают часы на минуту и снова читают время
- **THEN** первые два значения равны `2026-10-19T09:00:00Z`, а третье — `2026-10-19T09:01:00Z`

### Requirement: Генерация идентификаторов

По HLD §6.3 интерфейс `IDGenerator.NewID` SHALL возвращать ULID или ошибку. Боевая реализация SHALL использовать криптографически стойкий источник случайности. Тестовая реализация SHALL выдавать заданные ULID по порядку и сообщать об исчерпании последовательности.

#### Scenario: Последовательность ULID исчерпана

- **GIVEN** тестовой реализации заданы два разных допустимых ULID
- **WHEN** трижды вызывают `IDGenerator.NewID`
- **THEN** первые два вызова возвращают заданные значения по порядку, а третий возвращает ошибку

### Requirement: Выбор из переданного состава

По HLD §6.3 интерфейс `MemberChooser.Choose` SHALL возвращать участника только из переданного состава. Боевая реализация SHALL использовать криптографически стойкий источник случайности при выборе из нескольких участников, тестовая — заданного кандидата. Для пустого списка или заданного кандидата вне состава SHALL возвращаться ошибка.

#### Scenario: Выбор из одного участника

- **GIVEN** исходный список содержит одного участника
- **WHEN** боевая реализация выполняет `MemberChooser.Choose`
- **THEN** возвращается единственный участник без ошибки

#### Scenario: Детерминированный выбор из нескольких участников

- **GIVEN** в тестовой реализации выбран Bob из состава Alice, Bob и Carol
- **WHEN** выполняют `MemberChooser.Choose` с этим составом
- **THEN** возвращается Bob без ошибки

#### Scenario: Выбор невозможен

- **GIVEN** в отдельных прогонах список пуст либо тестовой реализации задан кандидат вне списка
- **WHEN** выполняют `MemberChooser.Choose`
- **THEN** каждый вызов возвращает ошибку и результат не содержит выбранного участника
