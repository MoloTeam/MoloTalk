# Design

## Context

Issue #7 опирается на HLD §3.3, §6.1–6.2 и клиентскую C3 из актуального отчёта. Рабочая ветка начинается от main. На этой базе web отсутствует, корень Caddy отвечает 503. PR #17 по #6 содержит публичные TypeScript-дескрипторы и типизированный бинарный Gateway. До слияния эти материалы используются для планирования интерфейсов. Сборка с реальными контрактами и итоговая проверка выполняются поверх принятого #6.

## Goals / Non-Goals

**Goals.** Запускаемая SPA, разбивка по C3, отдельно проверяемое состояние, подстановка двух транспортов и подключение готовой сборки к Caddy.

**Non-Goals.** Готовые продуктовые формы и бизнес-сценарии, автоматическое управление токенами, heartbeat и переподключение, восстановление после Ready, receipts, отправка или загрузка файлов, разработка серверных обработчиков. Срез добавляет необходимый каркас для таких задач.

## Decisions

### D1. Структура и маршруты

| Зона | Ответственность в #7 |
|---|---|
| app | Точка сборки, провайдер экземпляра приложения, layout и таблица маршрутов |
| features/access | Экраны входа и профиля как точки дальнейшей реализации |
| features/dialogs | Каркас списка диалогов, выбора диалога и области групп |
| features/composer | Основа редактора внутри маршрута диалога |
| features/timeline | Основа истории и статусов внутри маршрута диалога |
| sync | Порты и адаптеры, действия слоя обмена, передача результатов в состояние |
| state | Фабрика store, начальное состояние, выбранный диалог и данные контрольного сценария |

Предлагаемые клиентские пути: /, /login, /profile, /chats, /chats/:chatId. Это маршруты каркаса без решения о продуктовых перенаправлениях и проверке сессии. /chats/:chatId связывает список, историю и редактор одним параметром маршрута. Формы и экраны используют переданные действия и селекторы. UI не импортирует реализации сетевых адаптеров. Для небольшого каркаса достаточно типизированного store с явными действиями и подпиской, без обязательного выбора отдельной библиотеки состояния.

### D2. Конструирование приложения

Точка входа однажды создаёт store и передаёт его слою обмена вместе с API и WebSocket. React получает экземпляр через провайдер. Инициализация runtime отделена от рендера; подключение подписок идемпотентно на уровне их жизненного цикла, отключение освобождает обработчики. В тесте ту же фабрику вызывают с независимыми подстановками и фиксированными данными. Модульный singleton и общие изменяемые начальные коллекции не используются.

Для сквозной проверки каркаса достаточно одного вызова чтения через API-порт и одного принятого события через WebSocket-порт с наблюдаемым изменением store. Остальные действия появляются по мере реализации функций.

### D3. Транспорт и #6

Публичные generated-типы подключаются из репозиторного api-пакета без копирования и без импорта внутреннего пакета. Способ подключения должен одинаково работать в dev, тестах и сборке. В реализации проверяются фактические пути экспорта и разрешение зависимостей из принятого #6.

API-адаптер строит Connect-клиент для общего origin, принимает конфигурацию транспорта и сохраняет типизированные результаты, код ошибки и доступные метаданные. Нужен минимальный показательный метод чтения, например GetMe, на тестовом транспорте. WebSocket-адаптер поддерживает подключение, подписку, отправку и закрытие для бинарных GatewayEnvelope, использует утверждённый формат oneof и сообщает о повреждённых кадрах. Адрес /ws строится из origin приложения со схемой ws/wss по соответствию http/https. В тестах WebSocket подменяется на границе порта и отдельно проверяется бинарное кодирование адаптера. Управление сессией и обработка Ready по продуктовым правилам появятся в следующих карточках.

В dev запуск Vite показывает оболочку независимо от сервисов. Если нужно направить сетевые вызовы в локальное окружение, используется явная настройка разработки с документированным входом Caddy и доверенным CA. Нормальная сборка использует тот же origin для SPA, RPC и /ws. Заглушки подставляются точкой сборки тестов.

### D4. Единый вход и сборка

Предлагается собрать web и необходимые зависимости api на этапе сборки образа и перенести только dist в Caddy. Это сохраняет один опубликованный HTTPS-порт и позволяет использовать существующий Compose. Правила для RPC, /ws и служебной проверки прокси применяются до выдачи SPA. Fallback разрешается только для GET/HEAD известных маршрутов клиента; ассеты запрашиваются по обычному пути и отсутствующий ресурс возвращает 404. Проверки, ожидающие 503 на корне, обновляются вместе с правилами Caddy. Имеющиеся тесты запрещённых RPC, похожих путей и Upgrade сохраняются.

### D5. Порядок работ и приёмка

Этап 1 охватывает команды, каркас, маршруты, store и работу с двумя заглушками. Этап 2 начинается после попадания #6 в main: актуализация ветки, подключение репозиторного api, контрольный вызов через тестовый транспорт и двусторонняя проверка кадров. Этап 3 проверяет выдачу SPA через Caddy и сохранение маршрутизации существующих сервисов. Клиентская сборка и модульные тесты не требуют запуска backend. Проверки Caddy могут использовать уже существующие тестовые upstream.

## Risks / Trade-offs

- PR #17 может изменить публичные пути экспорта и DTO. Фиксация импорта и сборочная проверка привязаны к принятому main.
- Слишком широкий SPA fallback может вернуть HTML вместо ошибки API. Список клиентских маршрутов ограничивается таблицей приложения, а 404 и Upgrade проверяются через Caddy.
- Зависимости инициализации React могут создать общие подписки. Независимые экземпляры runtime и тест освобождения подписки проверяют жизненный цикл.
- Caddy должен видеть сборку из текущего исходного дерева. Чистый запуск Compose и проверка прямого маршрута входят в приёмку.

## Migration Plan

Данных для переноса нет. Выдача SPA на корне заменяет временный ответ 503 одновременно с подключением сборки клиента. При откате возвращаются исходная конфигурация Caddy и ответ 503; остальные сервисы сохраняют прежние маршруты.
