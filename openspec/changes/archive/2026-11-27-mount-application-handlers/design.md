# Дизайн подключения handlers

## Context

`bootstrap.Run` строит `Hosted`, конфиг и слушатель. `httpserver.Server.Handler` регистрирует два служебных маршрута. При штатной отмене вызов `Shutdown` ограничен пятью секундами, а ранний выход `Serve` может оставить goroutine ожидания контекста. Текущий `statusWriter` пишет HTTP статус, но не гарантирует проксирование интерфейсов upgrade.

## Goals / Non-Goals

- Сохранить совместимость входов и служебных маршрутов. Собрать прикладные handlers в композиции без импорта транспорта в use case.
- Сделать управляемыми нормальный выход, отказ регистрации/запуска, ошибка `Serve` и общий бюджет остановки.
- Прикладные порты и обработчики продукта, mTLS, Redis и NATS, Caddy routing и изменение proto рассматриваются в связанных карточках.

## Decisions

1. Добавить к уже используемым `Options` опциональную регистрацию транспорта до старта слушателя. Сохранить текущий `Hosted` и `Options` без новых обязательных полей или методов. Регистрация проходит через один mux, служебные пути резервируются. Конфликт маршрута или ошибка сборки возвращаются до начала обслуживания.
2. Логирование/request ID оборачивают общий HTTP mux с прикладными и служебными маршрутами. `statusWriter` передаёт поддерживаемые возможности ответа при upgrade. Использовать `Unwrap` и `http.ResponseController` там, где это поддерживается. Для выбранного механизма upgrade проверить фактический доступ к `http.Hijacker` и способ записи точного 101 без второго заголовка.
3. Владелец ресурса подключает проверку readiness и операцию закрытия в composition root. Общий lifecycle запускает и закрывает ресурсы под контекстом, освобождает их при ошибке старта или `Serve` и использует единый конечный бюджет. Для hijacked соединений HTTP Shutdown недостаточен, владелец транспорта получает сигнал остановки и закрывает их. Оставшийся слушатель закрывается при отказе остановки по бюджету. Существующие процессы без прикладных зависимостей сохраняют 200/503 на health/ready.
4. Использовать стандартную библиотеку Go и существующий Connect, новых производственных зависимостей не планируется. Для теста upgrade проверить руку WebSocket на loopback. Если понадобится новая тестовая библиотека, обоснование и лицензию внести в design до реализации.

## Risks / Trade-offs

Сбой маршрута и игнорирование отмены внутри адаптера осложняют cleanup. Репрезентативные тесты должны отдельно проверить отказ слушателя, ранний выход Serve, задержку readiness, отмену in-flight HTTP, активный upgrade и то, что shutdown не ждёт бесконечно.

## Migration Plan

Платформа сначала вливается с пустой опцией и test handlers. #9 и #31 подключают свои реальные функции в собственных ветках. Глобальный переход Compose с liveness на readiness остаётся в соответствующих вертикалях.

## Open Questions

Форма опций может быть уточнена на ревью дизайна при сохранении обратной совместимости. Для всех практически используемых механизмов upgrade требуется положительный тест.
