# Design

## Context

`main` на `068cdeb` содержит Go 1.27, npm workspaces под Node ≥ 24.11.1 и npm ≥ 11, Vitest в web, отдельные API-тесты с локальным Go-процессом и Buf v1.75.0. Tagged Go-тесты используют PostgreSQL 17 через Testcontainers. Матрица маршрутизации Caddy запускается из `deploy/tests/docker-compose.yml` с отдельными upstream. Сборка и тесты уже описаны в AGENTS.md, README и API README. HLD §5.4 задаёт изоляцию окружений.

Тело и комментарии #8 не удалось получить с GitHub. Предложение опирается на название карточки из среза, архитектурное ревью E08/Q9 и актуальный код. Перед apply сверить с карточкой и согласовать расхождения, особенно метрику и порог покрытия.

## Goals / Non-Goals

**Goals**

- Запускать существующие проверки из чистого checkout и получать отдельные статусы сборки, контрактов и интеграции.
- Получать воспроизводимый результат для ветки #8 до появления CI в `main`.

**Non-Goals**

- Настройка branch protection, deployment и GitHub Project. Живой браузерный E2E и отдельная автоматизация аудита остаются самостоятельными работами.

## Decisions

1. **GitHub Actions на Linux.** Разделить workflow на Go, web/API, contracts и контейнерные проверки, чтобы статус указывал на область сбоя. Для Go использовать версию из `backend/go.mod`, для web — закреплённую совместимую версию Node и корневой `npm ci`. API-тестам также нужен Go. Использовать официальные `actions/checkout` (MIT), `actions/setup-go` (MIT), `actions/setup-node` (MIT) и `actions/upload-artifact` (MIT) для checkout, provision и публикации. Закрепить ревизии по SHA: `checkout` v7.0.1 (`3d3c42e5aac5ba805825da76410c181273ba90b1`), `setup-go` v7.1.0 (`d8cbb8045d7f43706b9177cceb36c1f91a6644d5`), `setup-node` v7.1.0 (`949feb2413d6458794dcd2491c4babbbce0c15c1`), `upload-artifact` v7.0.2 (`cf430e030ddbb5b0abf93d22962f4752f3646cd9`), задать `contents: read` и ограничить длительность jobs. Linux даёт единое окружение для Docker и инструментов без дополнительной платформенной матрицы.
2. **Запуск первого workflow.** `pull_request` для `main` и `push` для `main` и `ci/8-quality-checks`; ручной `workflow_dispatch` включён для повторов после появления workflow в ветке по умолчанию. Публикация ветки, если её одобрит владелец, даст фактический запуск по `push` ещё до интеграции. [События GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push)
3. **Контракты.** Buf устанавливается по версии из API README (Apache-2.0). Использовать `buf format --diff --exit-code`, `buf lint`, `buf build`, `buf breaking` и четыре команды генерации из API README. База для PR — `base.sha`, для push в `main` — SHA до push, для ручного запуска на `main` — родитель проверяемого коммита. Для проверочной ветки используется общий предок с `origin/main`. Выгрузить модуль `api` базы с её lock и конфигурацией во временный каталог. Если база недоступна, завершить проверку с диагностикой. Выявлять изменённые и новые generated-файлы без обновления lock или golden в раннере.
4. **Изоляция Docker.** Запускать `go test -tags=integration -count=1 ./...` в `backend/` и существующую Compose-матрицу с уникальным именем проекта. Получить exit code контейнера `verify`, при отказе собрать диагностический вывод и выполнить `down -v --remove-orphans` для этого имени. Не поднимать демонстрационные данные из рабочей среды.
5. **Веб-покрытие.** Официальный `@vitest/coverage-v8` (MIT) закреплён на версии 3.2.7, совпадающей с Vitest из lockfile `main`. Провайдер даёт branch counts в JSON/LCOV и работает с текущими тестами. Область — рукописные TS/TSX в `web/src`, включая подходящие файлы без тестов. Исключения ограничены тестами, fixtures и декларациями `*.d.ts`. Добавление dev-зависимости отражено в общем lockfile. [Метаданные пакета](https://www.npmjs.com/package/@vitest/coverage-v8/v/3.2.7)
6. **Go-покрытие.** Стандартный `go test -coverprofile` публикуется отдельно как покрытие операторов. Для исходов решений выбран `gobco` v1.3.4 (BSD-2-Clause) в режиме `-branch`: проверено на Go 1.27.4, контрольный пакет с одним выполненным исходом даёт `Branch coverage: 1/2` и JSON с `FalseCount: 0`. Инструмент запускается по одному пакету (не поддерживает `./...`) и не учитывает build tags, поэтому `scripts/ci/go-coverage.sh` обходит пакеты в копии `backend` без `*_integration_test.go` и складывает отчёты. Область — пакеты `backend`, кроме `backend/gen`, `internal/testenv`, `internal/archtest` и `internal/platform/rpc/testserver`. В `internal/platform/rpc` два теста, читающие `api/testdata` вне модуля, пропускаются только в gobco-прогоне; обычный `go test` их выполняет. Ограничения: измеряются исходы булевых условий, `select` не покрывается, полное CFG-покрытие не заявляется. Порог не применяется. [Документация gobco](https://github.com/rillig/gobco#usage)
7. **Публикация отчётов.** `scripts/ci/coverage-report.mjs` проверяет наличие и непустоту отчётов, выводит числитель, знаменатель и область каждого измерения в сводку Actions и завершается ошибкой при отсутствии данных. Отчёты загружаются раздельными артефактами `go-coverage` и `web-coverage`. Исключены `backend/gen` и тестовые вспомогательные пакеты Go; остальные исключения и неизмеряемые конструкции документированы в `docs/ci.md`. Тесты и получение непустых отчётов являются проверками, порог применяется только по утверждённым критериям.

## Risks / Trade-offs

- Доступность Buf, registry или Docker → фиксированные версии и отдельная диагностика причин; запуск без кеша является контрольным.
- Разные метрики Go и web → показывать раздельные отчёты с областью измерения. Не суммировать числители и знаменатели между стеками.
- Пересечение с обновлением инструментов web или сверкой маршрутов → брать актуальный lockfile и доступные команды из базы. Новые проверки подключаются после появления, существующий workflow самодостаточен.

## Migration Plan

Подготовить workflow и локальный прогон в ветке #8. Проверить GitHub Actions по SHA ветки, если публикация согласована. Способ доставки результата в `main` и момент закрытия GitHub issue определяет владелец. Обычный процесс проекта требует PR, а для #8 пользователь попросил обойтись без его открытия. Изменения схемы, данных и конфигурации runtime не нужны.
