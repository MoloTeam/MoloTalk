# Database Migrations

## Purpose

Определяет создание, версионирование и проверку целостности схемы PostgreSQL, безопасное повторное применение миграций и диагностику отказов.

## ADDED Requirements

### Requirement: Схема создаётся на пустой БД

Начальная миграция SHALL создавать прикладную схему без отклонённого U06 на пару messages(channel_id,id), с ограничением текста C12 до 4096 символов.

#### Scenario: Начальная миграция применяется к пустой БД

- **GIVEN** пустая PostgreSQL-БД
- **WHEN** запускают миграции
- **THEN** миграции завершаются успешно и начальная версия отмечена выполненной

### Requirement: Повторное применение сохраняет данные

Миграции SHALL иметь стабильные версии и применяться по порядку. Повторный запуск SHALL пропускать выполненные миграции и сохранять прикладные данные. Одновременные запуски на одной БД SHALL сериализовать применение.

#### Scenario: Повторный запуск не меняет результат

- **GIVEN** все миграции применены и в БД сохранена контрольная запись пользователя
- **WHEN** миграции запускают повторно
- **THEN** команда завершается успешно, список применённых версий не получает дублей, контрольная запись сохранена

#### Scenario: Конкурентный запуск не выполняет миграцию дважды

- **GIVEN** пустая БД и два запуска миграционного механизма
- **WHEN** оба начинают подготовку одновременно
- **THEN** каждый успешно завершается после сериализации, каждая версия отмечена выполненной ровно один раз

### Requirement: Ошибка миграции останавливает подготовку

Каждая миграция начальной схемы SHALL выполняться атомарно. При SQL-ошибке её изменения SHALL откатываться, версия SHALL оставаться неприменённой и запуск SHALL завершаться с ненулевым кодом. Успешно выполненные ранее версии SHALL сохраняться.

#### Scenario: Ошибка внутри одной миграции

- **GIVEN** первая миграция выполнена, в следующей после корректного DDL добавлена заведомо ошибочная SQL-команда в изолированном тестовом наборе
- **WHEN** запускают миграционный механизм
- **THEN** предыдущая версия сохраняется, объекты ошибочной миграции отсутствуют, её версия не отмечена успешно выполненной и получен отказ

### Requirement: Уникальность обеспечивается PostgreSQL

Уникальные ограничения выбранной схемы SHALL отклонять конфликтующие записи. Минимальная проверка SHALL охватывать `users.identifier`, `channels.direct_pair_key` и ключ повтора сообщения `(channel_id,author_id,client_message_id)`.

#### Scenario: Дубликаты нарушают SQL-ограничение

- **GIVEN** валидные пользователи, диалог и сообщение, подготовленные в отдельной БД
- **WHEN** в независимых транзакциях пытаются повторить каждый указанный уникальный ключ с новым первичным ключом
- **THEN** каждый конфликт отклоняется PostgreSQL с SQLSTATE `23505`, исходная запись сохраняется

### Requirement: Ссылочная целостность проверяется при фиксации

Внешние ключи SHALL обеспечивать связи выбранной схемы. Ограничение `group_owner_is_member` SHALL оставаться `DEFERRABLE INITIALLY DEFERRED`, позволяя создать группу и её владельца-участника в одной транзакции.

#### Scenario: Ссылка на отсутствующую запись отклоняется

- **GIVEN** БД после миграций
- **WHEN** пытаются записать сообщение с отсутствующим автором или участника с отсутствующим каналом в независимых транзакциях
- **THEN** PostgreSQL отклоняет каждый случай с SQLSTATE `23503`

#### Scenario: Владелец добавлен в той же транзакции

- **GIVEN** существующий пользователь и новая группа с указанным владельцем
- **WHEN** группа и запись владельца в `channel_members` создаются одной транзакцией
- **THEN** транзакция успешно фиксируется

#### Scenario: Владелец отсутствует в составе при фиксации

- **GIVEN** существующий пользователь указан владельцем новой группы
- **WHEN** транзакцию фиксируют без записи владельца в `channel_members`
- **THEN** фиксация отклоняется с SQLSTATE `23503`, группа не сохраняется

### Requirement: CHECK отклоняют недопустимые значения

`CHECK` согласованной схемы SHALL отклонять недопустимую роль, нулевую revision, превышение 4096 символов текста и прочтение без доставки. Граничные допустимые значения SHALL приниматься.

#### Scenario: Допустимые границы принимаются

- **GIVEN** валидные связанные данные и предел длины текста 4096 символов
- **WHEN** записывают сообщение с текстом из 4096 символов, включая многобайтовые символы, и `revision=1`
- **THEN** PostgreSQL сохраняет сообщение

#### Scenario: Недопустимые значения отклоняются

- **GIVEN** валидная основа данных в отдельной БД
- **WHEN** в независимых транзакциях проверяют роль вне `ADMIN/MEMBER`, `revision=0`, текст из 4097 символов и `read_at` без `delivered_at`
- **THEN** PostgreSQL отклоняет каждый вариант с SQLSTATE `23514`, соответствующая запись не сохраняется

### Requirement: Безопасная диагностика подключения migrate

При недоступной БД или некорректном `DATABASE_URL` migrate SHALL завершаться ненулевым кодом. Сообщение и журнал SHALL содержать безопасную категорию ошибки без пароля и полной строки подключения.

#### Scenario: Некорректный DSN содержит контрольный секрет

- **GIVEN** заведомо некорректный DATABASE_URL содержит уникальный тестовый пароль
- **WHEN** запускают migrate с захватом stdout и stderr
- **THEN** код ненулевой, сообщение и журнал не содержат контрольного пароля и полного DSN

#### Scenario: Корректный DSN указывает на недоступную БД

- **GIVEN** корректный DATABASE_URL с уникальным тестовым паролем указывает на недоступный адрес
- **WHEN** запускают migrate с ограниченным контекстом ожидания
- **THEN** команда завершается ненулевым кодом, сообщение и журнал не содержат контрольного пароля и полного DSN

### Requirement: Одобренные CHECK действуют в PostgreSQL

C01, C02, C04, C08, C15, C17, C18 и C19 SHALL применяться по выражениям каталога design.md. Каждый отрицательный случай SHALL отклоняться PostgreSQL с SQLSTATE `23514`.

#### Scenario: Недопустимые значения отклоняются одобренными CHECK

- **GIVEN** валидные связанные данные, каждый случай выполняется отдельной транзакцией
- **WHEN** для каждого одобренного CHECK записывают недопустимые значения из таблицы
- **THEN** запись отклоняется с SQLSTATE `23514`, исходные данные сохранены

| CHECK | Недопустимые значения |
|---|---|
| C01 | ULID неверной длины или с символом вне допустимой маски |
| C02 | identifier длиной 0 или 255 либо ненормализованный регистр |
| C04 | expires_at равен created_at или меньше него |
| C08 | Непустое имя канала длиной 101 либо пустое имя |
| C15 | Неудалённое сообщение без непробельного текста и вложений |
| C17 | purpose вне AVATAR/MESSAGE_ATTACHMENT |
| C18 | status вне UPLOADING/VALIDATING/READY/REJECTED/DELETING |
| C19 | size_bytes меньше 0 |

### Requirement: Одобренные индексы присутствуют в схеме

Индексы sessions_user_idx, refresh_session_idx и login_window_cleanup_idx SHALL создаваться по user_id, session_id и window_started_at соответственно. Индекс attachment_cleanup_idx SHALL создаваться по паре (status, created_at) с условием linked_at IS NULL.

#### Scenario: Состав и определения индексов подтверждены

- **GIVEN** пустая БД после миграций
- **WHEN** читают определения четырёх индексов из pg_indexes
- **THEN** все четыре присутствуют с правильными ключами и предикатами, лишнего индекса от U06 нет

### Requirement: Отклонённый U06 не является зависимостью FK

Миграции SHALL сохранять FK на `messages(id)` и не создавать U06.

#### Scenario: FK не требуют отклонённого составного ключа

- **GIVEN** PostgreSQL-БД после миграций
- **WHEN** проверяют ограничения, индексы и внешние ключи, ссылающиеся на messages
- **THEN** U06 и его индекс отсутствуют, единственный внешний ключ на messages ссылается на один столбец
