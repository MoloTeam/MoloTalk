# Proposal

## Why

Веб-клиенту нужен общий каркас, чтобы компоненты входа, диалогов, редактора и истории могли разрабатываться параллельно. [Issue #7](https://github.com/MoloTeam/MoloTalk/issues/7) задаёт структуру по C3 и границы подмены зависимостей по HLD §3.3, §6.1–6.2.

## What Changes

- Создать приложение в `web/` на Vite, React и TypeScript с командами dev, lint, typecheck, test и build.
- Выделить шесть компонентов C3, маршрутизацию и точку сборки приложения. React вызывает действия приложения и отображает их результаты.
- Ввести подставляемые порты API и WebSocket и фабрику состояния на экземпляр приложения во вкладке.
- Подключить публичные сгенерированные контракты #6 к транспортным адаптерам. Заглушки позволяют разрабатывать и проверять клиентский каркас независимо от работающих сервисов.
- Подключить сборку клиента к единому HTTPS-входу Caddy с прямой загрузкой клиентских маршрутов.

## Capabilities

### New Capabilities

- `web-client-shell` — команды, модульная структура и клиентская навигация.
- `web-client-runtime` — подменяемые транспортные порты и изоляция состояния приложения.

### Modified Capabilities

- `ingress-routing` — заменить временный ответ 503 на корне выдачей SPA и сохранить маршрутизацию RPC и WebSocket.

## Impact

Затрагиваются `web/`, локальное окружение и его проверки, инструкции запуска и спецификация входного прокси. Основа адаптеров — публичный пакет из [PR #17 по #6](https://github.com/MoloTeam/MoloTalk/pull/17). Работу над каркасом, портами и тестовыми подстановками можно подготовить до слияния. Интеграция и приёмка выполняются по контракту #6 после его появления в main.

Граница #7 — каркас, транспортные адаптеры и проверка их подмены. Пользовательские сценарии, включая управление сеансом, загрузку файлов, повторные запросы после Ready и обновление истории, реализуются в карточках соответствующих функций. Этой карточке не назначены отдельные ФТ.
