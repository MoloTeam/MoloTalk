# 2 Архитектура приложения

<a name="section-2-1"></a>

## 2.1 Технологические решения

Для серверных компонентов был выбран Go, чтобы использовать единый язык реализации сетевых сервисов и конкурентной обработки подключений. Для браузерного клиента были выбраны React и TypeScript: компонентная структура отделяет представление от обмена данными и позволяет проверять формы и состояния независимо.

Таблица 1 – Основной технологический стек

| Область | Технология | Назначение | Обоснование |
| --- | --- | --- | --- |
| Клиент | React и TypeScript | Разработка веб-интерфейса | Компонентный подход, развитая экосистема и статическая типизация |
| Сервер | Go | Прикладные сервисы | Поддержка конкурентного выполнения, эффективная работа сетевых приложений и единый язык серверной разработки |
| Доступ | Caddy | HTTPS и маршрутизация | Единый origin API и соединений WebSocket |
| Запросы | ConnectRPC и JSON | Unary RPC поверх HTTPS | Контракты сервисов и единая модель ошибок |
| События клиенту | WebSocket и Protobuf | Постоянные соединения | Передача изменений всем активным сеансам |
| Данные | PostgreSQL | Постоянное состояние | Реляционные связи уникальность и локальные транзакции |
| Присутствие | Redis | Сроки жизни подключений | Быстрое обновление эфемерных записей с TTL |
| Файлы | S3 совместимое MinIO | Байты и миниатюры | Прямой PUT/GET по временным разрешениям |
| Брокер | NATS Core | Публикация и подписка | Доставка уведомлений работающим подписчикам |
| Запуск | Docker Compose | Общая среда | Декларативное описание многоконтейнерной системы. Упрощает первоначальное развертывание и локальную разработку. |

PostgreSQL выбран конечным хранилищем сообщений. Для хранения файлов будет использоваться S3 совместимое MinIO: сервис файлов проверяет объект и разрешение на доступ, но не становится каналом передачи пользовательских байтов. NATS Core используется как транспорт уведомлений.

<a name="section-2-2"></a>

## 2.2 Контекст системы

Пользователь ведёт переписку через MoloTalk. Владелец и администратор являются ролями пользователя внутри конкретной группы, а не отдельными внешними субъектами.

Граница системы охватывает браузерный клиент, серверные приложения и управляемую инфраструктуру.

<a name="section-2-3"></a>

## 2.3 Контейнеры и основные взаимодействия

Входной прокси направляет запросы сервисам и передаёт соединения WebSocket шлюзу. Auth, Chat и Media работают с общей PostgreSQL, Presence — с Redis. Файлы передаются между браузером и S3 напрямую.

Auth, Chat и Presence публикуют уведомления в NATS Core. Каждый Gateway подписывается самостоятельно, чтобы доставлять события своим соединениям. Служебные проверки сеансов и доступа выполняются через внутренние интерфейсы сервисов.

<a name="section-2-4"></a>

## 2.4 Внутреннее устройство сервиса аккаунтов

API аккаунтов преобразует запросы в команды прикладных компонентов. Правила паролей проверяют ввод, проверка пароля выполняет хеширование и сравнение, управление сеансами выпускает, ротирует и отзывает токены. Компонент аккаунтов изменяет профиль и проверяет аватар; репозиторий выполняет SQL.

<a name="section-2-5"></a>

## 2.5 Внутреннее устройство сервиса чатов

API чатов разбирает входные сообщения и передаёт команды прикладным компонентам. Управление группами владеет правилами состава и преемника; обработка сообщений – повторами, авторством и версиями; компонент подтверждений объединяет ACK; чтение состояния формирует страницы и представления. Общая политика доступа проверяет членство, роль и авторство. Репозиторий выполняет SQL через адаптер PostgreSQL.

Сообщение и строки его получателей фиксируются одной локальной транзакцией Chat. Привязка файлов и публикация выполняются после неё отдельными шагами.

<a name="section-2-6"></a>

## 2.6 Внутреннее устройство сервиса файлов

API файлов передаёт параметры загрузки и доступа прикладным компонентам. Проверка файла определяет реальный формат и размер; управление файлами координирует проверку, финальный ключ и очистку. Политика доступа проверяет владельца или текущее членство и ссылку из сообщения. Адаптер S3 читает объект для проверки и выдаёт временные разрешения; пользовательское скачивание выполняется напрямую из хранилища.

<a name="section-2-7"></a>

## 2.7 Внутреннее устройство сервиса присутствия

API присутствия принимает запросы статусов и служебные сведения от Gateway. Состояние учитывается по каждому соединению с серверным TTL. Пользователь считается ONLINE, пока существует хотя бы одно живое соединение. Политика видимости ограничивает выдачу статусов собеседниками и общими участниками; изменения публикуются после обновления состояния.

<a name="section-2-8"></a>

## 2.8 Внутреннее устройство шлюза событий

Транспорт отвечает за кадры, буферы и heartbeat. Проверка сеанса выполняет авторизацию; подписки сопоставляют соединение с текущей аудиторией; инициализация собирает READY из доступных чатов и отметок чтения. Рассылка разбирает события брокера, выбирает адресатов и передаёт кадры транспорту. Проверка аудитории выполняется независимо от своевременности уведомления об исключении из группы.

При восстановлении соединения READY инициирует повторное чтение текущих данных; журнал воспроизведения пропущенных событий не требуется.

<a name="section-2-9"></a>

## 2.9 Внутреннее устройство веб клиента

Компоненты форм и диалогов управляют представлением. Редактор ведёт черновик, загрузки и очередь повторной отправки; история отвечает за окна сообщений и прокрутку. Модуль обмена данными объединяет API и WebSocket с нормализованным состоянием. Изменения согласуются по id и revision, а после потери связи выполняется повторное чтение. Серверные проверки прав и лимитов не подменяются наличием кнопок в интерфейсе.

<a name="section-2-10"></a>

## 2.10 Сквозные сценарии и согласованность

При отправке текста Chat проверяет сеанс и членство, сохраняет сообщение и пытается опубликовать уведомление. Успешный ответ подтверждает принятие сервером. Gateway проверяет актуальную аудиторию и направляет событие всем подходящим подключениям, включая другие сеансы автора. Получение браузером подтверждается отдельным ACK; открытие активного видимого чата – подтверждением прочтения.

Для файла последовательность включает PrepareUpload, прямой PUT в S3 и CompleteUpload. Media проверяет фактический формат и размер, после чего объект становится READY. SendMessage записывает идентификаторы файлов, затем отдельным обновлением связывает их с чатом. Получатель запрашивает GetDownloadURL; Media проверяет членство и неудалённую ссылку из сообщения. Прямой GET выполняется браузером по выданному URL.

При отсутствии события клиент перечитывает список диалогов, загруженные диапазоны истории, роли, подтверждения и присутствие. Обновление выполняется при входе, открытии чата, reconnect, возвращении вкладки и периодически в активной вкладке. Замена полного загруженного диапазона исправляет пропущенные изменения и удаления; простого добавления новых записей недостаточно. Возможное временное расхождение устраняется последующей сверкой.

Без общей транзакции сбой после записи сообщения, но до привязки файлов не устраняется чтением истории: идентификаторы уже сохранены, а разрешающая связь может отсутствовать. Выполняются ограниченные повторы привязки и журналирование результата.
