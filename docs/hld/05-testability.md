# 5 Тестируемость

Тестируемость обеспечивается границами прикладных правил, явными портами зависимостей и контролируемым состоянием. Возможность подменить зависимость закладывается в конструкторы модулей; она не должна появляться только как специальная ветка поведения после написания тестов.

<a name="section-5-1"></a>

## 5.1 Границы модулей и размещение логики

Таблица 10 – Границы функциональных модулей

| Модуль | Интерфейсы | Логика внутри границы |
| --- | --- | --- |
| Веб-клиент | API adapter WebSocket adapter store | Преобразование действий и ответов в представление; очередь, загрузка окон, локальные состояния. Правила прав и лимитов подтверждаются сервером. |
| Аккаунты | Auth API; AccountRepository SessionRepository | Регистрация, уникальность идентификатора, пароль, профиль и сеансы. Контроллер только разбирает DTO и отображает ошибки. |
| Чаты | Chat API; GroupService MessageService ReceiptService QueryService | Роли, предел состава, преемник, авторство, повтор отправки и статусы. Репозитории не принимают продуктовые решения. |
| Файлы | Media API; AttachmentRepository ObjectStorage | Назначение, формат, размер, готовность, право выдачи ссылки и жизненный цикл объекта. |
| Присутствие | Presence API; PresenceStateStore | TTL каждого соединения, объединение нескольких сеансов и видимость статуса. |
| Gateway | WebSocket adapter; AuthClient ChatAccessClient EventSubscriber | Кадры, подписки и адресация. Права группы получает от Chat; бизнес-правила сообщений не дублирует. |

HTTP-контроллеры и обработчики WebSocket преобразуют транспортный ввод в команды и получают результат прикладного компонента. В обработчиках React находятся только действия представления и отображение ошибок. Проверка автора, разрешение роли, выбор преемника, лимит 100 и окончательная проверка файла выполняются доменными политиками, доступными без UI, сети и SQL.

Зависимости передаются через конструкторы. Прикладной компонент зависит от интерфейса с контекстом операции и типизированной ошибкой; конкретные PostgreSQL, Redis, S3 и NATS подключаются в точке сборки процесса. Прямые обращения к глобальному пулу, брокеру или файловой системе из доменной политики исключаются.

Проверка формата принимает поток байтов, а не путь к локальному файлу. Благодаря этому повреждённое изображение, слишком большой объект, незавершённый DOCX или ошибка чтения воспроизводятся потоком в памяти. В интеграционной среде те же порты связываются с настоящими инфраструктурными адаптерами.

<a name="section-5-3"></a>

## 5.3 Управление состоянием временем и случайностью

Текущее время получает Clock.Now, идентификаторы – IDGenerator.NewID, выбор преемника – MemberChooser. Токены и временные ссылки получают срок через конфигурацию и свои адаптеры. В боевом контуре используются системные часы и криптографически стойкие источники, а в проверках – фиксированная шкала времени и заранее заданная последовательность значений.

~~~go
type Clock interface { Now() time.Time }
~~~

~~~go
type IDGenerator interface { NewID() (ID, error) }
~~~

~~~go
type MemberChooser interface { Choose([]UserID) (UserID, error) }
~~~

Например, Clock возвращает 2026-10-19T09:00:00Z, генератор выдаёт последовательность фиксированных ULID, MemberChooser выбирает указанного кандидата из отсортированного списка. Проверка передачи владения не зависит от случайного результата и порядка обхода коллекции. Ветвь без администраторов проверяется всеми допустимыми кандидатами.

TTL присутствия, истечение токена и интервалы клиентского обновления проверяются продвижением управляемого времени и планировщика. Ожидание произвольного sleep не используется как доказательство завершения. Таймеры получают Scheduler с отменой; тест явно запускает нужное срабатывание. Условия успешности проверяются по результату API и состоянию.

Каждая проверка получает отдельный контекст и набор данных. Глобальный изменяемый кеш не связывает разные сценарии. Клиентское состояние создаётся фабрикой на вкладку; обработчики событий могут подключаться к изолированному store. Для гонок сохранение сообщения, Link и Publish имеют отдельные наблюдаемые точки, позволяющие воспроизвести частичный результат без общей транзакции.

## 5.4 Тестовое окружение и данные

Работоспособная копия системы формируется единым описанием Docker Compose: веб-клиент, прокси, пять серверных сервисов, PostgreSQL, Redis, NATS Core и MinIO. Интернет-сервисы для основного сценария не требуются. Адреса, ключи, bucket и времена жизни задаются конфигурацией окружения; сервисные credentials отличны от пользовательских токенов.

Таблица 12 – Состав проверочных окружений

| Уровень | Состав | Условия воспроизведения |
| --- | --- | --- |
| Компонентные проверки | Прикладной модуль в процессе | In-memory repositories, ObjectStorage fake, записывающий Publisher, Clock и IDGenerator. |
| Проверки адаптеров | PostgreSQL Redis NATS MinIO | Настоящие SQL-ограничения, транзакции, подписи URL и транспорт подписок в изолированных контейнерах. |
| Сквозная проверка | Полный Compose и браузеры | Два пользователя, несколько вкладок/устройств; отдельный прогон с двумя Gateway. |
| Подготовка | Миграции seed bucket readiness | Сначала инфраструктура, затем схема и данные, затем сервисы и прокси; готовность проверяется до сценария. |
| Очистка | Отдельная БД и префикс объектов прогона | После сценария удаляются только его данные; рабочие пользовательские данные не используются. |

Подготовка выполняется по шагам: создание отдельной базы и bucket; применение миграций; загрузка фиксированных пользователей и объектов; запуск Redis/NATS; запуск сервисов; ожидание readiness; открытие браузерных сеансов. Начальное состояние именуется набором fixture и создаётся заново для каждого прогона. Копирование случайной рабочей базы не используется.

Базовый набор содержит Alice, Bob и Carol, личный диалог Alice–Bob и группу с владельцем Alice, администратором Bob и участником Carol. Дополнительные наборы задают 99/100 участников, отсутствующего администратора, непрочитанные сообщения, файлы на границах 5/20 МБ и 5/6 вложений, валидные и повреждённые форматы. Пароли и ключи в этом контуре являются тестовыми и не совпадают с рабочими.

Отказы зависимостей задаются на границах портов: ошибка записи, потерянный ответ после успешного INSERT, отказ Link, ошибка Publish, изменение членства перед выдачей кадра. Для настоящих адаптеров дополнительно проверяются перезапуск подключения и недоступность контейнера. Это позволяет отличать гарантии БД от поведения заглушки, не добавляя тестовую бизнес-логику в контроллеры.

## 5.5 Наблюдаемость и признаки завершения

Каждой операции назначается request_id, передаваемый через X-Request-Id и журналы сервисов. Структурированная запись содержит сервис, операцию, пользователя, идентификатор чата/сообщения, результат и время выполнения. Для отправки отдельно фиксируются message_saved, attachments_linked и publish_result. Пароли, токены и содержимое файлов в журнал не включаются.

Таблица 13 – Признаки успешного завершения

| Операция | Внешний результат | Проверяемое состояние |
| --- | --- | --- |
| Создание группы | HTTP 200 и Chat | В БД есть группа владелец и весь состав; число не превышает 100. |
| Отправка сообщения | HTTP 200 и messageId | Одна запись по clientMessageId; GetMessages возвращает её. Наличие события не является обязательным доказательством записи. |
| Получение и прочтение | Успешный ACK и receipts | delivered_at/read_at сохранены у исходного получателя; READ подразумевает delivered_at. Итоговый статус читается автором. |
| Файл | CompleteUpload и READY | Объект существует по финальному ключу; ссылка сообщения и привязка проверяются отдельно; получатель получает допустимый GET URL. |
| Выход | Успешный Logout и экран входа | Сеанс отозван; другие независимые сеансы остаются действующими. |
| Присутствие | GetPresence и состояние TTL | ONLINE при любом живом соединении, OFFLINE после истечения последнего. |

Метрики включают число и длительность запросов по результатам, ошибки сохранения и привязки, ошибки публикации и число активных соединений. /healthz подтверждает работу процесса, /readyz – готовность обязательных зависимостей сервиса. Отказ NATS у Chat учитывается как деградация уведомлений и не отменяет доступность сохранения в работающей БД. Для Media обязательна возможность проверить объект в S3, для Presence – доступность Redis.

Приёмочные проверки различают сохранение и доставку сообщения, готовность файла и его привязку. При ошибке Link проверяются промежуточное состояние и отказ шага. Повторное чтение API не считается ремонтом привязки.
